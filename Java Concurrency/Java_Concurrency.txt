Java Concurrency — Short Interview Notes
-----------------------------------------

1. Concurrency vs Parallelism
Concurrency

Multiple tasks make progress during overlapping time periods.

Tasks may execute interleaved on a single CPU/core.

Main goal: structure/manage multiple tasks.

Parallelism

Multiple tasks execute at the same time on multiple CPU cores.

Main goal: reduce execution time / increase throughput.

Concurrency ≠ Parallelism
Parallelism is one way to achieve concurrency.

Example:

Concurrency:  A → B → A → C → B
              (interleaving)

Parallelism:  Core 1 → A A A
              Core 2 → B B B

2. Ways to Achieve Concurrency
At a high level:

Concurrency
├── Processes
├── Threads
├── Async / Non-blocking I/O
├── Event-driven programming
├── Actors / message passing
└── Distributed systems

In Java, most interviews focus on:

Threads
ExecutorService
CompletableFuture
ForkJoinPool
Virtual Threads
Concurrent Collections
Locks / Synchronizers
Atomic classes
Java Memory Model

3. Process vs Thread
Process
Independent execution unit.

Own memory/address space.

Expensive to create/switch.

Communication requires IPC mechanisms.

Thread
Execution unit inside a process.

Threads share process heap/resources.

Has its own:

Stack

Program counter

Thread-local state

Cheaper than processes.

Process
 ├── Heap
 ├── Resources
 ├── Thread 1 → Stack
 ├── Thread 2 → Stack
 └── Thread 3 → Stack

4. Java Thread
A thread represents an independent path of execution.

Thread t = new Thread(() -> {
    System.out.println("Running");
});

t.start();

Important:

t.start(); // creates/schedules new thread
t.run();   // normal method call; NO new thread

5. Multithreading
Multithreading = executing multiple threads within a process.

Benefits:

Responsiveness

Better CPU utilization

Overlap computation and I/O

Higher throughput

Resource sharing

Problems:

Race conditions

Deadlocks

Starvation

Livelocks

Context-switch overhead

Visibility issues

Contention

6. Ways to Create/Manage Threads in Java
Traditional
extends Thread

or

implements Runnable

or

implements Callable<T>

Preferred in production
Use ExecutorService rather than manually creating threads.

ExecutorService executor =
    Executors.newFixedThreadPool(10);

executor.submit(() -> doWork());

executor.shutdown();

Why?

Task submission
      ↓
Executor
      ↓
Thread Pool
      ↓
Worker Threads

Separates task from thread management.

7. Executor Framework
Core abstractions:

Executor
   ↓
ExecutorService
   ↓
ThreadPoolExecutor

Important methods:

execute()

shutdown()
shutdownNow()
awaitTermination()

Common pool types
Executors.newFixedThreadPool(n)
Executors.newCachedThreadPool()

8. Thread Pool
A thread pool maintains reusable worker threads.

Instead of:

Request → create thread
Request → create thread
Request → create thread

use:

Requests
   ↓
Work Queue
   ↓
Thread Pool
 ├── T1
 ├── T2
 ├── T3
 └── T4

Advantages:

Avoid thread creation overhead

Control concurrency

Bound resource usage

Queue tasks

Improve throughput

Key parameters:

corePoolSize
maximumPoolSize
keepAliveTime
workQueue
ThreadFactory
RejectedExecutionHandler

9. Runnable vs Callable
Runnable
Runnable r = () -> doSomething();

No return value

Cannot directly throw checked exception

Callable
Callable<Integer> c = () -> calculate();

Returns value

Can throw checked exception

Future<Integer> future = executor.submit(c);

Integer result = future.get();

10. Future
Future<T> represents the result of an asynchronous computation.

Future<String> f = executor.submit(() -> fetch());

String result = f.get();

Problem:

f.get();

can block.

Limitations of traditional Future:

Difficult composition

Difficult chaining

Blocking retrieval

Poor error-composition model

This is where CompletableFuture becomes important.

11. CompletableFuture
Used for asynchronous computation and composition.

CompletableFuture
    .supplyAsync(() -> fetchUser())
    .thenApply(user -> user.getName())
    .thenAccept(System.out::println);

Important operations:

thenApply       → transform result
thenCompose     → flatten dependent async operation
thenCombine     → combine independent operations
allOf           → wait for multiple futures
anyOf           → first completed
exceptionally   → recover
handle          → success + failure handling
whenComplete    → observe completion

thenApply vs thenCompose
thenApply:
A → B

thenCompose:
A → Future<B>

If you already have an async operation, thenCompose usually avoids nested futures.

12. CompletableFuture Execution
Two important forms:

thenApply(...)
thenApplyAsync(...)

Async variants may execute asynchronously using an executor, commonly the ForkJoinPool.commonPool() when no executor is supplied.

For production code, explicitly providing the appropriate executor can be important:

thenApplyAsync(fn, executor)

13. Synchronization
Synchronization coordinates access to shared mutable state.

Common mechanisms:

synchronized
Lock
ReadWriteLock
StampedLock
Semaphore
CountDownLatch
CyclicBarrier
Phaser
Atomic classes
Concurrent Collections

14. synchronized
Provides:

Mutual exclusion

Memory visibility / happens-before guarantees

synchronized void increment() {
    count++;
}

or:

synchronized (lock) {
    count++;
}

Only one thread can hold the same monitor at a time.

15. Race Condition
Occurs when correctness depends on unpredictable interleaving of threads accessing shared state.

Example:

count++;

is conceptually:

read count
add 1
write count

Two threads can both read the same value.

T1: read 10
T2: read 10
T1: write 11
T2: write 11

Expected: 12
Actual:   11

16. Atomicity
An operation is atomic when it appears indivisible to other threads.

Examples:

AtomicInteger counter = new AtomicInteger();

counter.incrementAndGet();

Common atomic classes:

AtomicInteger
AtomicLong
AtomicBoolean
AtomicReference
LongAdder
LongAccumulator

17. volatile
volatile primarily provides:

Visibility

Ordering constraints

It does not generally provide compound-operation atomicity.

volatile boolean running = true;

If one thread writes:

running = false;

other threads can observe the updated value.

But:

volatile int count;

count++; // NOT atomic

because it is read-modify-write.

18. Java Memory Model — JMM
The Java Memory Model defines how threads interact with memory and what values they are guaranteed to observe.

Three concepts are especially important:

Atomicity
Visibility
Ordering

Visibility
One thread's write becomes observable by another.

Ordering
Compiler/JIT/CPU may reorder operations unless constrained by the memory model.

Happens-before
If A happens-before B, the effects of A are guaranteed to be visible to B.

Important happens-before relationships include:

unlock → subsequent lock on same monitor
volatile write → subsequent volatile read
Thread.start() → actions in started thread
actions in thread → successful Thread.join()

19. synchronized vs volatile
synchronized	volatile
Visibility	✅	✅
Mutual exclusion	✅	❌
Compound atomicity	✅	❌
Locking	✅	❌
Typical use	Critical section	State/flag visibility

Interview phrase:

volatile is about visibility and ordering; synchronized additionally provides mutual exclusion.

20. Lock
java.util.concurrent.locks.Lock

Example:

Lock lock = new ReentrantLock();

lock.lock();
try {
    // critical section
} finally {
    lock.unlock();
}

Advantages over basic synchronized:

tryLock()
lockInterruptibly()
timed lock acquisition
multiple Conditions

21. ReentrantLock
Reentrant means the same thread can acquire the lock multiple times.

Thread T
  ↓
lock()
  ↓
method A
  ↓
method B
  ↓
lock() again

It must release correspondingly.

22. ReadWriteLock
Useful when:

Many readers
Few writers

Provides:

Read Lock  → multiple readers
Write Lock → exclusive

But don't automatically assume it improves performance—contention, workload, and read/write duration matter.

23. StampedLock
Supports:

Read lock
Write lock
Optimistic read

Optimistic reads can reduce locking overhead when writes are uncommon.

But StampedLock is not reentrant.

24. Semaphore
Controls the number of threads allowed to access a resource.

Semaphore semaphore = new Semaphore(10);

Conceptually:

10 permits

Thread → acquire → resource
Thread → release → permit returned

Useful for limiting concurrent access to:

Connections

External APIs

Expensive resources

25. CountDownLatch
Allows one or more threads to wait until a counter reaches zero.

CountDownLatch latch = new CountDownLatch(3);

Worker 1 → countDown()
Worker 2 → countDown()
Worker 3 → countDown()

Main → await()
             ↓
          continue

One-shot synchronization mechanism.

26. CyclicBarrier
Allows a fixed group of threads to wait for each other.

T1 ─┐
T2 ─┼── barrier ──→ continue
T3 ─┘

Unlike CountDownLatch, a barrier can be reused.

27. Concurrent Collections
Important ones:

ConcurrentHashMap
CopyOnWriteArrayList
ConcurrentLinkedQueue
BlockingQueue
ConcurrentSkipListMap
ConcurrentSkipListSet

ConcurrentHashMap
Thread-safe map optimized for concurrent access.

ConcurrentHashMap<K, V>

Prefer atomic compound operations when appropriate:

map.computeIfAbsent(key, k -> createValue());

28. BlockingQueue
Designed for producer-consumer scenarios.

Producer
   ↓
BlockingQueue
   ↓
Consumer

Methods include:

put()
take()
offer()
poll()

put() can block when capacity is unavailable; take() can block when empty.

29. CopyOnWriteArrayList
Excellent when:

Reads >> Writes

Every mutation creates a new underlying array.

Good examples:

Listener lists

Configuration snapshots

Mostly-read collections

Bad for write-heavy workloads.

30. Thread Safety
A class is thread-safe if its behavior remains correct when accessed concurrently according to its contract.

Ways to achieve it:

Immutability
Synchronization
Locks
Atomics
Thread confinement
Concurrent collections
Message passing
Stateless design

Immutable objects
Often the easiest concurrency strategy.

Example:

final class User {
    private final String name;
    ...
}

If state never changes, synchronization requirements can be dramatically reduced.

31. Thread Confinement
Keep mutable state owned by one thread.

Thread 1 → owns object A
Thread 2 → owns object B

No sharing → fewer synchronization problems.

ThreadLocal is one mechanism for thread-confined state.

32. ThreadLocal
Provides per-thread storage.

ThreadLocal<String> context =
    ThreadLocal.withInitial(() -> "default");

Conceptually:

Thread 1 → value A
Thread 2 → value B
Thread 3 → value C

Important with thread pools: clean up ThreadLocal state when appropriate because worker threads are reused.

33. Deadlock
Two or more threads wait forever for each other's locks.

T1: holds A → waits for B
T2: holds B → waits for A

Four Coffman conditions:

1. Mutual exclusion
2. Hold and wait
3. No preemption
4. Circular wait

Common prevention strategy:

Always acquire multiple locks in a globally consistent order.

34. Livelock
Threads are active but make no useful progress.

T1 → gives way to T2
T2 → gives way to T1
T1 → gives way again
...

Unlike deadlock, threads aren't necessarily blocked.

35. Starvation
A thread waits indefinitely because other threads continually get access to required resources.

Possible causes:

Unfair locking

Excessive priority differences

Poor scheduling

Resource monopolization

36. Context Switching
CPU switches execution from one thread to another.

Costs include:

Saving/restoring CPU state

Scheduler overhead

Cache effects

Reduced CPU efficiency

Therefore:

More threads ≠ automatically more performance.

37. CPU-Bound vs I/O-Bound
CPU-bound
Examples:

Sorting
Compression
Complex calculations
Image processing

Performance depends primarily on CPU.

Usually use a bounded pool related to available CPU resources.

I/O-bound
Examples:

Database
HTTP calls
File I/O
Network calls

Threads may spend substantial time waiting.

Concurrency strategy can therefore differ significantly.

38. ForkJoinPool
Designed for tasks that can be recursively divided into smaller tasks.

Big Task
 ├── Task A
 │    ├── A1
 │    └── A2
 └── Task B
      ├── B1
      └── B2

Uses work stealing.

One worker can steal work from another worker's queue when idle.

Used by:

Parallel streams

CompletableFuture async operations by default in many cases

Explicit Fork/Join workloads

39. Parallel Streams
list.parallelStream()
    .map(...)
    .filter(...)
    .toList();

Can use multiple threads.

Good candidate when operations are:

Independent

CPU-intensive

Suitable for splitting

Potential problems:

Shared mutable state

Blocking I/O

Common pool contention

Small datasets where overhead dominates

Ordering/collector considerations

40. Virtual Threads — Java 21+
Very important for modern Java interviews.

Virtual threads are lightweight threads managed by the JVM rather than being directly mapped one-to-one to OS threads.

Thread.startVirtualThread(() -> {
    handleRequest();
});

Or:

try (var executor =
         Executors.newVirtualThreadPerTaskExecutor()) {

    executor.submit(() -> handleRequest());
}

Useful especially for high-concurrency, I/O-heavy applications.

Conceptually:

Many virtual threads
        ↓
Few carrier/platform threads
        ↓
CPU

They make thread-per-task designs much more scalable for many blocking workloads.

They do not make CPU computation faster.

41. Platform Thread vs Virtual Thread
Platform Thread	Virtual Thread
Managed by	OS/JVM	JVM
Cost	Higher	Much lower
Huge concurrency	Limited	Much higher
I/O-heavy workloads	Can require pools	Very suitable
CPU speed	Same underlying CPU	Same underlying CPU
Thread-per-request	Can be expensive	Much more practical

42. Structured Concurrency
Modern Java direction for managing related concurrent tasks as a unit.

Concept:

Parent task
 ├── Child task A
 ├── Child task B
 └── Child task C

The lifetime and failure handling of child tasks are tied to the parent scope.

For interviews, understand the motivation:

Make concurrent task lifecycles, cancellation, errors, and ownership easier to reason about.

43. Async vs Multithreading
Asynchronous programming means the caller doesn't necessarily wait synchronously for an operation to complete.

Multithreading means multiple threads execute.

They are related but not identical.

You can have:

Async + threads
Async + event loop
Concurrency + single thread

For example, non-blocking event-loop systems can handle many concurrent operations with relatively few threads.

44. Blocking vs Non-blocking
Blocking
Thread waits for operation:

result = databaseCall(); // thread waits

Non-blocking
Thread can continue doing other work while operation progresses.

Commonly associated with:

Callbacks
Futures
CompletableFuture
Reactive programming
NIO
Event loops

45. Atomic CAS
Many Java atomic operations use CAS — Compare-And-Set.

Concept:

Expected = 10
Actual   = 10

CAS(10, 11)
       ↓
success

If another thread changed it:

Expected = 10
Actual   = 12

CAS(10, 11)
       ↓
failure

CAS enables many lock-free/non-blocking algorithms.

46. ABA Problem
With CAS:

A → B → A

A thread may see A and incorrectly assume nothing changed.

Solutions can include versioning/stamps, e.g. concepts represented by:

AtomicStampedReference

47. Lock-Free vs Wait-Free
Lock-free
System as a whole makes progress even if individual threads can starve.

Wait-free
Every thread completes its operation within a bounded number of steps.

Generally:

Wait-free → stronger guarantee
Lock-free → weaker guarantee

Know these for senior-level concurrency discussions.

48. Producer-Consumer
Classic concurrency pattern:

Producer(s)
    ↓
 BlockingQueue
    ↓
Consumer(s)

Benefits:

Decoupling

BlockingQueue<Task>

49. Backpressure
When producers generate work faster than consumers can process it:

Producer rate > Consumer rate
             ↓
        queue grows
             ↓
       memory/resource risk

Backpressure means controlling production/acceptance of work so the system remains stable.

Very relevant for high-scale backend/SSE/event-driven systems.

53. Thread Interruption
Threads can be interrupted to signal cancellation.

Thread t = new Thread(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        // do work
    }
});

t.start();
t.interrupt(); // sets interrupt flag

Important patterns:

if (Thread.interrupted()) {
    // handle interruption
    // clears the flag
}

Blocking methods like sleep(), wait(), join() throw InterruptedException when interrupted.

Best practice: propagate InterruptedException or restore interrupt status.

54. Daemon Threads
Daemon threads are background threads that don't prevent JVM exit.

Thread daemon = new Thread(() -> {
    while (true) {
        // background work
    }
});
daemon.setDaemon(true);
daemon.start();

When all non-daemon threads finish, JVM exits even if daemon threads are running.

Use cases: background cleanup, monitoring, periodic tasks.

55. Thread Priority
Each thread has a priority (1-10).

t.setPriority(Thread.MAX_PRIORITY); // 10
t.setPriority(Thread.NORM_PRIORITY); // 5
t.setPriority(Thread.MIN_PRIORITY); // 1

Important: Thread priority is only a hint to the scheduler. Don't rely on it for correctness.

56. Fair vs Unfair Locks
ReentrantLock can be fair or unfair.

// Unfair (default, faster)
Lock unfairLock = new ReentrantLock();

// Fair (threads acquire in FIFO order)
Lock fairLock = new ReentrantLock(true);

Fair locks prevent starvation but have higher overhead due to queue management.

Unfair locks allow barging and are generally faster but may cause starvation.

57. CompletableFuture Error Handling
Important error handling patterns:

CompletableFuture.supplyAsync(() -> riskyOperation())
    .exceptionally(ex -> {
        // recover from error
        return defaultValue;
    });

CompletableFuture.supplyAsync(() -> riskyOperation())
    .handle((result, ex) -> {
        if (ex != null) {
            // handle error
            return fallback;
        }
        return result;
    });

CompletableFuture.supplyAsync(() -> riskyOperation())
    .whenComplete((result, ex) -> {
        // observe result or error
    });

58. ExecutorService Shutdown Patterns
Proper shutdown is critical for production.

ExecutorService executor = Executors.newFixedThreadPool(10);

// Graceful shutdown
executor.shutdown(); // stops accepting new tasks
try {
    if (!executor.awaitTermination(60, TimeUnit.SECONDS)) {
        executor.shutdownNow(); // force shutdown
    }
} catch (InterruptedException e) {
    executor.shutdownNow();
    Thread.currentThread().interrupt();
}

shutdownNow() returns list of unexecuted tasks.

59. Thread Dump Analysis
Thread dumps help diagnose concurrency issues.

Generating thread dumps:

jstack <pid> > thread_dump.txt

Or programmatically:

Map<Thread, StackTraceElement[]> allStackTraces = Thread.getAllStackTraces();

Common thread states to understand:

RUNNABLE: executing or ready to run
BLOCKED: waiting for monitor lock
WAITING: waiting indefinitely (wait(), join(), park())
TIMED_WAITING: waiting with timeout (sleep(), wait(timeout))
TERMINATED: completed execution

60. ScopedValue — Java 21+
Modern alternative to ThreadLocal for structured concurrency.

ScopedValue<String> CONTEXT = ScopedValue.newInstance();

ScopedValue.where(CONTEXT, "user123")
    .run(() -> {
        // CONTEXT is bound here
        doWork();
    });

Unlike ThreadLocal, ScopedValue is automatically unbound when the scope ends.

Better for structured concurrency and virtual threads.

61. Thread Pool Sizing Guidelines
CPU-bound tasks:

pool size ≈ number of CPU cores

I/O-bound tasks:

pool size can be larger, often based on latency ratio

Formula:

threads = cores * (1 + wait_time / compute_time)

Or use dynamic sizing with newCachedThreadPool or custom policies.

62. ConcurrentHashMap Internals
Important implementation details:

Java 7: Segment-based locking (striped locks)
Java 8+: Bucket-level locking with CAS + synchronized

Key operations:

put(): uses CAS for empty buckets, synchronized for collisions
get(): lock-free (volatile reads)
computeIfAbsent(): atomic compound operation

Size calculation: uses LongAdder for better performance under contention.

63. Phaser
Advanced synchronization barrier for dynamic thread sets.

Phaser phaser = new Phaser();

phaser.register(); // register main thread

for (int i = 0; i < n; i++) {
    phaser.register();
    new Thread(() -> {
        doWork();
        phaser.arriveAndAwaitAdvance();
    }).start();
}

phaser.arriveAndAwaitAdvance(); // wait for all

Unlike CyclicBarrier, Phaser supports:
- Dynamic party registration
- Multiple phases
- Termination

64. Exchanger
Allows two threads to exchange objects at a synchronization point.

Exchanger<String> exchanger = new Exchanger<>();

// Thread 1
String myData = "data1";
String received = exchanger.exchange(myData);

// Thread 2
String myData = "data2";
String received = exchanger.exchange(myData);

Use case: genetic algorithms, pipeline handoffs.

65. BlockingQueue Implementations
Different implementations for different needs:

ArrayBlockingQueue: bounded, array-backed
LinkedBlockingQueue: optionally bounded, linked nodes
PriorityBlockingQueue: priority-ordered
DelayQueue: elements with delay
SynchronousQueue: direct handoff (no storage)
LinkedTransferQueue: tryTransfer, transfer operations

66. CompletableFuture Composition Patterns
Advanced composition:

// Multiple independent futures
CompletableFuture.allOf(f1, f2, f3).join();

// First to complete
CompletableFuture.anyOf(f1, f2, f3).join();

// Timeout
CompletableFuture.supplyAsync(() -> longOperation())
    .orTimeout(5, TimeUnit.SECONDS);

// Retry pattern
CompletableFuture.supplyAsync(() -> operation())
    .exceptionallyCompose(ex -> retry());

67. Virtual Threads Limitations
Virtual threads have limitations:

- Not suitable for CPU-bound work (doesn't make it faster)
- Should not use synchronized blocks (can pin carrier threads)
- ThreadLocal usage can cause memory bloat
- Not compatible with some native code
- Thread priorities not supported

Best for: I/O-bound, high-concurrency, blocking operations.

68. Reactive Programming with Java
While not core Java, important to know:

Project Reactor / RxJava provide:

Flux<T>: 0..N elements
Mono<T>: 0..1 elements

Flux.just(1, 2, 3)
    .map(i -> i * 2)
    .filter(i -> i > 2)
    .subscribe();

Benefits: non-blocking, backpressure-aware, composable.

69. Performance Monitoring
Key metrics for concurrent systems:

- Thread pool utilization
- Queue lengths
- Rejection rates
- Task execution times
- Context switch rate
- Lock contention
- GC impact under concurrency

Tools: JMX, VisualVM, YourKit, async-profiler.

70. Common Concurrency Bugs
Watch out for:

- Double-checked locking without volatile
  Can lead to partially constructed objects being visible to other threads.

- Using notify() instead of notifyAll()
  May wake the wrong thread, causing missed signals.

- Forgetting to unlock in finally block
  Can cause deadlocks if exceptions occur.

- Holding locks during I/O
  Increases contention and can cause performance issues.

- String interning causing contention
  Interned strings are shared globally and can become contention points.

- Improper use of ThreadLocal with thread pools
  ThreadLocal values can leak across tasks when threads are reused.

- Missing volatile for flags
  Changes may not be visible to other threads.

- Incorrect happens-before assumptions
  Assuming visibility without proper synchronization.

71. Final Summary — Key Takeaways
For Java concurrency interviews, remember:

Core Concepts
- Concurrency ≠ Parallelism
- Thread safety requires atomicity, visibility, and ordering
- The Java Memory Model defines these guarantees

Execution Models
- ExecutorService > manual thread creation
- CompletableFuture for async composition
- ForkJoinPool for recursive divide-and-conquer
- Virtual threads for I/O-heavy, high-concurrency workloads

Synchronization
- synchronized: mutual exclusion + visibility
- volatile: visibility + ordering only
- Lock: more flexible than synchronized
- Atomic classes: lock-free operations

Thread Safety Strategies
- Immutability (simplest)
- Thread confinement
- Synchronization/locks
- Concurrent collections
- Atomic operations

Common Pitfalls
- More threads ≠ more performance
- volatile ≠ atomic
- ConcurrentHashMap ≠ automatic compound operation safety
- Virtual threads ≠ faster CPU execution

Best Practices
- Always release locks in finally blocks
- Handle InterruptedException properly
- Use appropriate thread pool sizes for workload
- Prefer immutable objects when possible
- Understand the difference between CPU-bound and I/O-bound workloads

Modern Java (21+)
- Virtual threads for scalable I/O
- ScopedValue for structured concurrency
- Structured concurrency for task lifecycle management

Remember: The right concurrency approach depends on your specific workload, resource constraints, and correctness requirements.
