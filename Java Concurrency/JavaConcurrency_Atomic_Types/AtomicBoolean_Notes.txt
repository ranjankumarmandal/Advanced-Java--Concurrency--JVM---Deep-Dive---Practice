AtomicBoolean - Short Notes

What is AtomicBoolean?
- Thread-safe boolean value
- Provides atomic operations without synchronized keyword
- Uses CAS (Compare-And-Swap) for lock-free operations
- Part of java.util.concurrent.atomic package
- Wrapper around volatile boolean with atomic operations

Key Methods:
- get() - read current value
- set(value) - set new value
- getAndSet(value) - return old, set new
- compareAndSet(expected, newValue) - update only if matches expected
- lazySet(value) - set with delayed visibility (performance optimization)

Why Use AtomicBoolean?
- No need for synchronized keyword
- Lock-free algorithm using CAS
- Better performance than synchronized blocks
- No thread blocking
- Simple API for boolean operations
- Useful for flags and state indicators

When to Use AtomicBoolean:
- Shutdown flags for threads
- One-time initialization flags
- State machine transitions
- Feature toggles
- Lock acquisition/release indicators
- Event notification flags
- When you need atomic read-modify-write operations on boolean

Benefits vs Synchronized:
- No thread blocking/waiting
- Lower overhead
- Better cache performance
- Avoids deadlocks
- Simpler code for basic operations
- Non-blocking algorithm
- Volatile semantics built-in

Limitations:
- Only works on single boolean value
- Not suitable for complex multi-variable operations
- CAS can fail under high contention (spin loops)
- Not a replacement for all synchronization needs
- Limited to boolean operations only

When NOT to Use:
- Complex operations involving multiple variables
- When you need to lock multiple resources together
- When operations are not atomic by nature
- When you need fairness guarantees
- When you need to wait/notify patterns

CAS (Compare-And-Swap) for Boolean:
-----------------------------------
How CAS Works with Boolean:
1. Read current boolean value from memory
2. Compare with expected boolean value
3. If matches, update to new boolean value atomically
4. If doesn't match, operation fails (retry or handle)

CAS Operation Flow:
- CPU instruction: cmpxchg on x86
- Atomic: all three steps happen as one indivisible operation
- Optimistic: assumes no contention, retries if conflict occurs

CAS Pseudocode for Boolean:
```
boolean compareAndSet(boolean expected, boolean newValue) {
    if (currentValue == expected) {
        currentValue = newValue;
        return true;
    }
    return false;
}
```

Boolean CAS Characteristics:
- Only two possible values (true/false)
- Simpler than integer/long CAS
- Less contention possible (only 2 states)
- Often used for one-time transitions (false -> true)

Memory Model & Visibility:
--------------------------
Happens-Before Relationship:
- Atomic operations establish happens-before
- Guarantees visibility across threads
- No need for volatile separately

Volatile Semantics:
- AtomicBoolean has volatile-like semantics
- Writes are immediately visible to other threads
- Prevents reordering of operations
- Underlying field is volatile

Memory Barrier Effects:
- StoreStore barrier before write
- StoreLoad barrier after write
- LoadLoad barrier before read
- LoadStore barrier after read

Visibility Guarantees:
- get() always sees latest set() value
- All atomic methods have full visibility
- No stale reads across threads
- Changes are immediately visible to other threads

LazySet vs Set:
---------------
What is lazySet()?
- Sets value without full memory barrier
- Delayed visibility to other threads
- Performance optimization
- Useful when immediate visibility not required

set() Behavior:
- Full memory barrier
- Immediate visibility to all threads
- Happens-before relationship established
- Slower but safer

lazySet() Behavior:
- No full memory barrier
- Visibility delayed (eventually consistent)
- No happens-before guarantee
- Faster but less safe

When to Use lazySet():
- Setting shutdown flag (thread will check periodically)
- One-time initialization where exact timing doesn't matter
- Performance-critical code where visibility delay acceptable
- When you control all access patterns

When NOT to Use lazySet():
- When immediate visibility required
- When other threads depend on immediate state change
- Critical state transitions
- When correctness depends on visibility timing

Performance Characteristics:
----------------------------
Lock-Free vs Lock-Based:
- Lock-free: no thread blocking
- Lock-based: threads can block waiting
- AtomicBoolean: lock-free using CAS

Contention Levels:
- Low contention: excellent performance
- Medium contention: good performance with retries
- High contention: performance degrades (spin loops)
- Boolean has limited contention (only 2 states)

CAS Spin Loop:
```
while (!compareAndSet(expected, newValue)) {
    expected = get();  // re-read current value
    // retry
}
```

Performance Comparison:
- AtomicBoolean vs synchronized: 2-10x faster (low contention)
- AtomicBoolean vs volatile: supports read-modify-write
- AtomicBoolean vs Boolean wrapper: thread-safe

When CAS Fails:
- Under high contention, CAS can fail repeatedly
- CPU wastes cycles in spin loops
- Consider backoff strategies
- Consider synchronized for very high contention

Common Patterns:
---------------
1. Shutdown Flag Pattern
   - Use set(true) to signal shutdown
   - Threads check get() periodically
   - No need for immediate visibility
   - Can use lazySet() for performance

2. One-Time Initialization Pattern
   - Use compareAndSet(false, true)
   - Ensures initialization runs exactly once
   - Thread-safe without synchronization
   - Common for singleton initialization

3. Lock Pattern (Simple Spin Lock)
   - compareAndSet(false, true) to acquire
   - set(false) to release
   - Can cause spin loops under contention
   - Consider backoff for better performance

4. State Machine Pattern
   - Use boolean to represent state
   - Atomic transitions between states
   - Useful for simple two-state machines
   - For complex states, use AtomicInteger/Enum

5. Feature Toggle Pattern
   - Use AtomicBoolean for runtime feature flags
   - Can be changed dynamically
   - Thread-safe reads and writes
   - Useful for A/B testing

Advanced Usage:
---------------
compareAndSet() for One-Time Actions:
- Ensures code runs exactly once
- Common pattern for initialization
- Thread-safe without locks
- Returns true if operation succeeded

getAndSet() for Toggle Operations:
- Returns previous value
- Sets new value atomically
- Useful for toggle logic
- Can detect state changes

lazySet() for Performance:
- Use when immediate visibility not required
- Reduces memory barrier overhead
- Good for flags checked periodically
- Not suitable for critical sections

Spin Lock with Backoff:
```java
AtomicBoolean lock = new AtomicBoolean(false);

public void acquireLock() {
    int attempts = 0;
    while (!lock.compareAndSet(false, true)) {
        attempts++;
        if (attempts > 10) {
            Thread.yield();  // or LockSupport.parkNanos
        }
    }
}

public void releaseLock() {
    lock.set(false);
}
```

Common Pitfalls:
----------------
1. Check-Then-Act Race Condition
   WRONG:
   ```java
   if (!flag.get()) {
       // Another thread might change here
       flag.set(true);
   }
   ```
   RIGHT:
   ```java
   flag.compareAndSet(false, true);
   ```

2. Assuming Atomicity Across Multiple Operations
   - Only single operations are atomic
   - Multiple operations need additional sync
   - Compound operations require careful design

3. Ignoring CAS Failure
   - Always check return value
   - Don't assume compareAndSet will succeed
   - Handle failure appropriately

4. Using lazySet() Incorrectly
   - Don't use when immediate visibility needed
   - Can cause subtle bugs
   - Understand visibility implications

5. Forgetting Visibility
   - AtomicBoolean provides visibility
   - Regular boolean does NOT
   - Don't mix with non-atomic access

6. Spin Lock Without Backoff
   - Can cause CPU thrashing
   - Add backoff for high contention
   - Consider using LockSupport

7. Using for Complex State
   - Boolean only has 2 states
   - Not suitable for multi-state machines
   - Use AtomicInteger or Enum for complex state

   public class Singleton {
       private static volatile Singleton instance;
       private static final AtomicBoolean initialized = new AtomicBoolean(false);

       public static Singleton getInstance() {
           if (instance == null) {
               synchronized (Singleton.class) {
                   if (instance == null && initialized.compareAndSet(false, true)) {

5. Bounded Semaphore with AtomicBoolean
   ```java
   public class SimpleSemaphore {
       private final AtomicInteger permits;
       private final AtomicBoolean[] slots;

       public SimpleSemaphore(int maxPermits) {
           this.permits = new AtomicInteger(maxPermits);
           this.slots = new AtomicBoolean[maxPermits];
           for (int i = 0; i < maxPermits; i++) {
               slots[i] = new AtomicBoolean(true);
           }
       }

       public boolean acquire() {
           for (int i = 0; i < slots.length; i++) {
               if (slots[i].compareAndSet(true, false)) {
                   permits.decrementAndGet();
                   return true;
               }
           }
           return false;
       }

       public void release(int slotIndex) {
           if (slotIndex >= 0 && slotIndex < slots.length) {
               slots[slotIndex].set(true);
               permits.incrementAndGet();
           }
       }
   }
   ```

Performance Tuning:
-------------------
1. Cache Line Padding
   - AtomicBoolean already has @Contended annotation in Java 8+
   - Prevents false sharing from cache lines
   - Important for high-frequency updates
   - Reduces cache coherence traffic

2. Contention Reduction Strategies
   - Use thread-local flags when possible
   - Reduce frequency of updates
   - Batch operations
   - Use lazySet() for non-critical updates

3. Backoff Strategies
   ```java
   public void acquireWithBackoff(AtomicBoolean lock) {
       int attempts = 0;
       while (!lock.compareAndSet(false, true)) {
           attempts++;
           if (attempts < 5) {
               Thread.yield();
           } else if (attempts < 10) {
               LockSupport.parkNanos(1000);
           } else {
               LockSupport.parkNanos(10000);
           }
       }
   }
   ```

Comparison with Other Mechanisms:
---------------------------------
AtomicBoolean vs Volatile Boolean:
- AtomicBoolean: supports read-modify-write operations
- Volatile: only supports simple read/write
- AtomicBoolean: compareAndSet for atomic updates
- Volatile: no atomic compound operations
- AtomicBoolean: slightly higher overhead
- Volatile: lower overhead for simple reads/writes

AtomicBoolean vs Synchronized:
- AtomicBoolean: lock-free, non-blocking
- Synchronized: can block threads
- AtomicBoolean: better performance under low contention
- Synchronized: better under high contention
- AtomicBoolean: no fairness guarantees
- Synchronized: provides fairness
- AtomicBoolean: simpler for single operations
- Synchronized: better for complex operations

AtomicBoolean vs ReentrantLock:
- AtomicBoolean: simpler, less overhead
- ReentrantLock: more features (tryLock, timeout, interruptible)
- AtomicBoolean: lock-free
- ReentrantLock: can block
- AtomicBoolean: no reentrancy
- ReentrantLock: supports reentrancy
- AtomicBoolean: good for simple flags
- ReentrantLock: good for critical sections

AtomicBoolean vs CountDownLatch:
- AtomicBoolean: reusable, state can change back
- CountDownLatch: one-time use, counts down to zero
- AtomicBoolean: simple boolean state
- CountDownLatch: counter-based synchronization
- AtomicBoolean: for flags and state
- CountDownLatch: for waiting on multiple events

Debugging AtomicBoolean Issues:
------------------------------
Common Problems and Solutions:

1. Stale Reads
   - Cause: Not using AtomicBoolean for shared access
   - Solution: Ensure all accesses go through AtomicBoolean
   - Check: Look for direct field access

2. Unexpected State Changes
   - Cause: Race conditions in compound operations
   - Solution: Use compareAndSet for atomic updates
   - Check: Review check-then-act patterns

3. Performance Degradation
   - Cause: High contention on CAS operations
   - Solution: Add backoff, use lazySet, consider alternatives
   - Check: Profile CAS failure rates

4. Visibility Issues
   - Cause: Using lazySet() incorrectly
   - Solution: Use set() when immediate visibility needed
   - Check: Review lazySet() usage

5. Deadlock-like Behavior
   - Cause: Spin loops without backoff
   - Solution: Add timeouts or backoff
   - Check: Look for infinite retry loops

Debugging Tools:
- JConsole / VisualVM for monitoring
- Thread dumps to see blocked threads
- JFR (Java Flight Recorder) for profiling
- Async profiler for CPU analysis
- YourKit for detailed profiling

2. Rate Limiter with Circuit Breaker
   ```java
   public class AdvancedCircuitBreaker {
       private final AtomicBoolean circuitOpen = new AtomicBoolean(false);
       private final AtomicBoolean halfOpen = new AtomicBoolean(false);
       private final AtomicInteger failureCount = new AtomicInteger(0);
       private final AtomicInteger successCount = new AtomicInteger(0);
       private final int failureThreshold;
       private final int successThreshold;

       public boolean allowRequest() {
           if (circuitOpen.get()) {
               if (halfOpen.compareAndSet(false, true)) {
                   successCount.set(0);
                   return true;
               }
               return false;
           }
           return true;
       }

       public void recordSuccess() {
           if (halfOpen.get()) {
               if (successCount.incrementAndGet() >= successThreshold) {
                   circuitOpen.set(false);
                   halfOpen.set(false);
                   failureCount.set(0);
               }
           }
       }

       public void recordFailure() {
           if (!circuitOpen.get()) {
               if (failureCount.incrementAndGet() >= failureThreshold) {
                   circuitOpen.set(true);
                   halfOpen.set(false);
               }
           } else {
               halfOpen.set(false);
           }
       }
   }
   ```

4. Cache Invalidation Strategy
   ```java
   public class CacheManager<K, V> {
       private final Map<K, V> cache = new ConcurrentHashMap<>();
       private final AtomicBoolean isValid = new AtomicBoolean(true);
       private final AtomicBoolean refreshInProgress = new AtomicBoolean(false);

       public V get(K key) {
           if (!isValid.get()) {
               waitForRefresh();
           }
           return cache.get(key);
       }

       public void invalidate() {
           isValid.lazySet(false);
       }

       public void refresh() {
           if (refreshInProgress.compareAndSet(false, true)) {
               try {
                   cache.clear();
                   loadFreshData();
                   isValid.set(true);
               } finally {
                   refreshInProgress.set(false);
               }
           }
       }

       private void waitForRefresh() {
           while (refreshInProgress.get()) {
               LockSupport.parkNanos(1000000);
           }
       }
   }
   ```

Anti-Patterns to Avoid:
-----------------------
1. Using AtomicBoolean as Mutex
   WRONG:
   ```java
   while (!lock.compareAndSet(false, true)) {
       // No backoff - CPU thrashing
   }
   ```
   RIGHT: Use ReentrantLock or add backoff

2. Ignoring Return Value of compareAndSet
   WRONG:
   ```java
   flag.compareAndSet(false, true);
   // Assumes it succeeded
   ```
   RIGHT: Check return value and handle failure

3. Using lazySet() for Critical State
   WRONG:
   ```java
   criticalState.lazySet(true);
   // Other threads might not see this immediately
   ```
   RIGHT: Use set() for critical state changes

4. Compound Operations Without Sync
   WRONG:
   ```java
   if (flag.get()) {
       doSomething();
       flag.set(false);
   }
   ```
   RIGHT: Use compareAndSet or additional synchronization

5. Mixing Atomic and Non-Atomic Access
   WRONG:
   ```java
   private boolean flag;  // Not atomic
   private AtomicBoolean atomicFlag;
   ```
   RIGHT: Use AtomicBoolean for all shared access

6. Using for Complex State Machines
   WRONG:
   ```java
   private final AtomicBoolean state1 = new AtomicBoolean(false);
   private final AtomicBoolean state2 = new AtomicBoolean(false);
   private final AtomicBoolean state3 = new AtomicBoolean(false);
   ```
   RIGHT: Use Enum or AtomicInteger for complex state

7. Spin Lock Without Timeout
   WRONG:
   ```java
   while (!lock.compareAndSet(false, true)) {
       // Infinite loop possible
   }
   ```
   RIGHT: Add timeout or backoff
