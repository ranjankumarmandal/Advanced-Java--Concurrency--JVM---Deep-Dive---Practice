AtomicLong - Short Notes

What is AtomicLong?
- Thread-safe primitive long value
- Provides atomic operations without synchronized keyword
- Uses CAS (Compare-And-Swap) for lock-free operations
- Part of java.util.concurrent.atomic package

Key Methods:
- get() - read current value
- set(value) - set new value
- getAndSet(value) - return old, set new
- getAndAdd(delta) / addAndGet(delta) - atomic addition
- getAndIncrement() / incrementAndGet() - atomic increment
- getAndDecrement() / decrementAndGet() - atomic decrement
- compareAndSet(expected, newValue) - update only if matches expected
- getAndUpdate(function) - apply function, return old value
- updateAndGet(function) - apply function, return new value
- accumulateAndGet(value, function) - accumulate with function
- getAndAccumulate(value, function) - accumulate, return old

Why Use AtomicLong?
- No need for synchronized keyword
- Lock-free algorithm using CAS
- Better performance than synchronized blocks
- No thread blocking
- Better scalability under high contention
- Simple API for common operations

When to Use AtomicLong:
- Shared counters in multithreaded applications
- Sequence number generation
- Statistics tracking
- Simple shared state without complex synchronization
- When you need atomic read-modify-write operations
- When performance is critical and contention is moderate

Benefits vs Synchronized:
- No thread blocking/waiting
- Lower overhead
- Better cache performance
- Avoids deadlocks
- Simpler code for basic operations
- Non-blocking algorithm

Limitations:
- Only works on single variables
- Not suitable for complex multi-variable operations
- CAS can fail under high contention (spin loops)
- Not a replacement for all synchronization needs

When NOT to Use:
- Complex operations involving multiple variables
- When you need to lock multiple resources together
- When operations are not atomic by nature
- When you need fairness guarantees

CAS (Compare-And-Swap) Mechanism:
---------------------------------
CAS is the fundamental operation that makes AtomicLong work without locks.

How CAS Works:
1. Read current value from memory
2. Compare with expected value
3. If matches, update to new value atomically
4. If doesn't match, operation fails (retry or handle)

CAS Operation Flow:
- CPU instruction: cmpxchg on x86
- Atomic: all three steps happen as one indivisible operation
- Optimistic: assumes no contention, retries if conflict occurs

CAS Pseudocode:
```
boolean compareAndSet(long expected, long newValue) {
    if (currentValue == expected) {
        currentValue = newValue;
        return true;
    }
    return false;
}
```

ABA Problem:
-----------
What is ABA Problem?
- Thread A reads value X
- Thread B changes X to Y, then back to X
- Thread A's CAS succeeds even though value changed
- Can cause issues in certain algorithms

ABA Problem Example:
- Initial: sharedRef = ObjectA
- Thread1: reads ObjectA, pauses
- Thread2: changes to ObjectB, then back to ObjectA
- Thread1: CAS(ObjectA, ObjectC) succeeds
- But ObjectA is a different instance than original!

Solutions to ABA:
- AtomicStampedReference (adds version stamp)
- AtomicMarkableReference (adds boolean mark)
- Use version numbers in your own logic

Memory Model & Visibility:
--------------------------
Happens-Before Relationship:
- Atomic operations establish happens-before
- Guarantees visibility across threads
- No need for volatile separately

Volatile Semantics:
- AtomicLong has volatile-like semantics
- Writes are immediately visible to other threads
- Prevents reordering of operations

Memory Barrier Effects:
- StoreStore barrier before write
- StoreLoad barrier after write
- LoadLoad barrier before read
- LoadStore barrier after read

Visibility Guarantees:
- get() always sees latest set() value
- All atomic methods have full visibility
- No stale reads across threads

Performance Characteristics:
----------------------------
Lock-Free vs Lock-Based:
- Lock-free: no thread blocking
- Lock-based: threads can block waiting
- AtomicLong: lock-free using CAS

Contention Levels:
- Low contention: excellent performance
- Medium contention: good performance with retries
- High contention: performance degrades (spin loops)

CAS Spin Loop:
```
while (!compareAndSet(expected, newValue)) {
    expected = get();  // re-read current value
    // retry
}
```

Performance Comparison:
- AtomicLong vs synchronized: 2-10x faster (low contention)
- AtomicLong vs volatile: supports read-modify-write
- LongAdder vs AtomicLong: LongAdder better for high contention

When CAS Fails:
- Under high contention, CAS can fail repeatedly
- CPU wastes cycles in spin loops
- Consider LongAdder for high-contention counters
- Consider synchronized for very high contention

Code Examples:
--------------
Example 1: Simple Counter
```java
AtomicLong counter = new AtomicLong(0);

// Thread 1
counter.incrementAndGet();

// Thread 2
counter.incrementAndGet();

// Result: counter = 2 (guaranteed)
```

Example 2: Compare-And-Set Pattern
```java
AtomicLong balance = new AtomicLong(100);

// Withdraw only if sufficient funds
long current = balance.get();
long newBalance = current - 50;
if (balance.compareAndSet(current, newBalance)) {
    System.out.println("Withdrawal successful");
} else {
    System.out.println("Withdrawal failed (concurrent modification)");
}
```

Example 3: Functional Update
```java
AtomicLong value = new AtomicLong(10);

// Apply function atomically
long result = value.updateAndGet(x -> x * 2);
// value = 20, result = 20

long oldResult = value.getAndUpdate(x -> x + 5);
// value = 25, oldResult = 20
```

Example 4: Accumulate Pattern
```java
AtomicLong sum = new AtomicLong(0);

// Accumulate values
sum.accumulateAndGet(5, Long::sum);  // sum = 5
sum.accumulateAndGet(10, Long::sum); // sum = 15
sum.accumulateAndGet(3, Long::sum);   // sum = 18
```

Example 5: Lazy Initialization
```java
AtomicLong cachedValue = new AtomicLong(-1);

long getValue() {
    long cached = cachedValue.get();
    if (cached == -1) {
        cached = computeExpensiveValue();
        cachedValue.compareAndSet(-1, cached);
    }
    return cachedValue.get();
}
```

Common Patterns:
---------------
1. Counter Pattern
   - Use incrementAndGet() for simple counters
   - Thread-safe without synchronization

2. Sequence Generator
   - Use getAndIncrement() for unique IDs
   - Each thread gets unique sequence number

3. Max/Min Tracking
   - Use updateAndGet() with Math.max/min
   - Track maximum value seen across threads

4. Circular Buffer Index
   - Use getAndIncrement() with modulo
   - Thread-safe index for circular buffers

5. Reference Counting
   - incrementAndGet() for acquire
   - decrementAndGet() for release
   - Check for zero to cleanup

Advanced Methods:
-----------------
getAndUpdate():
- Applies function, returns old value
- Useful when you need previous value
- Function must be side-effect free

updateAndGet():
- Applies function, returns new value
- Useful when you need updated value
- Function must be side-effect free

accumulateAndGet():
- Combines current value with accumulator
- Uses accumulator function (e.g., Long::sum)
- Returns new value after accumulation

getAndAccumulate():
- Combines current value with accumulator
- Returns old value before accumulation
- Useful for logging old values

Functional Method Example:
```java
AtomicLong number = new AtomicLong(5);

// Square the value
long squared = number.updateAndGet(x -> x * x);
// number = 25, squared = 25

// Get old, then update
long old = number.getAndUpdate(x -> x / 5);
// number = 5, old = 25
```

Common Pitfalls:
----------------
1. Check-Then-Act Race Condition
   WRONG:
   ```java
   if (atomic.get() > 0) {
       // Another thread might change here
       atomic.decrementAndGet();
   }
   ```
   RIGHT:
   ```java
   while (true) {
       long current = atomic.get();
       if (current <= 0) break;
       if (atomic.compareAndSet(current, current - 1)) break;
   }
   ```

2. Assuming Atomicity Across Multiple Operations
   - Only single operations are atomic
   - Multiple operations need additional sync

3. Ignoring CAS Failure
   - Always handle compareAndSet failure
   - Don't assume it will always succeed

4. Using in Loops Without Backoff
   - Can cause CPU thrashing
   - Consider adding backoff/retry logic

5. Forgetting Visibility
   - AtomicLong provides visibility
   - Regular long does NOT

LongAdder vs AtomicLong:
------------------------
What is LongAdder?
- Introduced in Java 8
- Designed for high-contention scenarios
- Uses striping to reduce contention
- Better performance under heavy write load

How LongAdder Works:
- Maintains array of cell values (stripes)
- Each thread updates different cell (reduces contention)
- sum() method combines all cells for total
- Trade-off: higher memory usage

Performance Comparison:
- Low contention: AtomicLong is faster (simpler)
- Medium contention: Comparable performance
- High contention: LongAdder significantly faster (3-10x)
- Read-heavy: AtomicLong better (sum() has overhead)

When to Use LongAdder:
- Statistics collection (counters, metrics)
- High-frequency updates
- Many threads updating same counter
- When exact current value not needed frequently
- When you can tolerate small delays in sum()

When to Use AtomicLong:
- Need exact current value frequently
- Low to medium contention
- Memory-constrained environments
- When you need compareAndSet semantics
- When you need atomic read-modify-write

LongAdder Example:
```java
LongAdder counter = new LongAdder();

// Multiple threads increment
counter.increment();  // Thread 1
counter.increment();  // Thread 2
counter.add(5);       // Thread 3

// Get total (not atomic with updates)
long total = counter.sum();  // Returns 7
```

LongAccumulator:
----------------
What is LongAccumulator?
- More flexible version of LongAdder
- Custom accumulation function
- Can perform max, min, or custom operations
- Also uses striping for performance

LongAccumulator Example:
```java
// Track maximum value
LongAccumulator max = new LongAccumulator(Long::max, Long.MIN_VALUE);
max.accumulate(10);
max.accumulate(5);
max.accumulate(20);
// max.get() = 20

// Track minimum value
LongAccumulator min = new LongAccumulator(Long::min, Long.MAX_VALUE);
min.accumulate(10);
min.accumulate(5);
min.accumulate(20);
// min.get() = 5
```

Performance Tuning:
-------------------
Optimizing CAS Operations:
1. Reduce Contention
   - Use thread-local variables when possible
   - Batch updates instead of frequent small updates
   - Consider LongAdder for high-contention counters

2. Backoff Strategies
   ```java
   // Exponential backoff
   int attempts = 0;
   while (!atomic.compareAndSet(expected, newValue)) {
       Thread.sleep(1 << attempts);  // 1, 2, 4, 8ms...
       attempts++;
       expected = atomic.get();
   }
   ```

3. Cache Line Padding
   - AtomicLong already has @Contended annotation
   - Prevents false sharing from cache lines
   - Important for high-frequency updates

4. Warm-up JVM
   - JIT compilation improves performance
   - Run benchmarks after warm-up
   - Use -XX:CompileThreshold for tuning

Benchmarking Tips:
- Use JMH (Java Microbenchmark Harness)
- Avoid dead code elimination
- Run multiple iterations
- Include warm-up phase
- Measure different contention levels

JMH Example Structure:
```java
@Benchmark
@Threads(4)
public long benchmarkAtomicLong() {
    return atomicLong.incrementAndGet();
}

@Benchmark
@Threads(4)
public void benchmarkLongAdder() {
    longAdder.increment();
}
```

Real-World Use Cases:
---------------------
1. Request Counter in Web Server
   ```java
   public class RequestMetrics {
       private final AtomicLong requestCount = new AtomicLong(0);
       private final AtomicLong errorCount = new AtomicLong(0);
       private final LongAdder responseTimeSum = new LongAdder();

       public void recordRequest(boolean success, long responseTime) {
           requestCount.incrementAndGet();
           if (!success) {
               errorCount.incrementAndGet();
           }
           responseTimeSum.add(responseTime);
       }

       public double getErrorRate() {
           return (double) errorCount.get() / requestCount.get();
       }
   }
   ```

2. Unique ID Generator
   ```java
   public class IdGenerator {
       private final AtomicLong sequence = new AtomicLong(0);

       public long nextId() {
           return sequence.getAndIncrement();
       }
   }
   ```

3. Rate Limiter
   ```java
   public class RateLimiter {
       private final AtomicLong tokens;
       private final long maxTokens;
       private final long refillInterval;

       public boolean tryConsume() {
           while (true) {
               long current = tokens.get();
               if (current <= 0) return false;
               if (tokens.compareAndSet(current, current - 1)) {
                   return true;
               }
           }
       }
   }
   ```

4. Circular Buffer Index
   ```java
   public class CircularBuffer<T> {
       private final T[] buffer;
       private final AtomicLong writeIndex = new AtomicLong(0);
       private final int capacity;

       public void put(T item) {
           long index = writeIndex.getAndIncrement() % capacity;
       buffer[(int) index] = item;
       }
   }
   ```

5. Reference Counting
   ```java
   public class ReferenceCounted {
       private final AtomicLong refCount = new AtomicLong(1);

       public void retain() {
           refCount.incrementAndGet();
       }

       public void release() {
           if (refCount.decrementAndGet() == 0) {
               cleanup();
           }
       }
   }
   ```

6. Sequence Number for Messages
   ```java
   public class MessageSequencer {
       private final AtomicLong sequence = new AtomicLong(0);

       public long nextSequence() {
           return sequence.incrementAndGet();
       }

       public void reset() {
           sequence.set(0);
       }
   }
   ```

Debugging AtomicLong Issues:
----------------------------
Common Problems and Solutions:

1. Unexpected Values
   - Check for race conditions in surrounding code
   - Verify all accesses go through AtomicLong
   - Look for non-atomic compound operations

2. Performance Degradation
   - Monitor CAS failure rate
   - Check contention levels
   - Consider LongAdder for high contention
   - Profile with VisualVM or JProfiler

3. Memory Visibility Issues
   - Ensure no direct access to underlying value
   - Check for improper use of lazySet()
   - Verify happens-before relationships

4. Deadlock-like Behavior
   - CAS spin loops can appear as deadlock
   - Check for infinite retry loops
   - Add timeouts to retry logic

Debugging Tools:
- JConsole / VisualVM for monitoring
- Thread dumps to see blocked threads
- JFR (Java Flight Recorder) for profiling
- Async profiler for CPU analysis

Logging CAS Failures:
```java
int failures = 0;
while (!atomic.compareAndSet(expected, newValue)) {
    failures++;
    if (failures > 100) {
        log.warn("High CAS contention: {} failures", failures);
    }
    expected = atomic.get();
}
```

Testing AtomicLong Code:
------------------------
Unit Testing Strategies:

1. Basic Functionality Tests
   ```java
   @Test
   public void testIncrement() {
       AtomicLong counter = new AtomicLong(0);
       assertEquals(1, counter.incrementAndGet());
       assertEquals(1, counter.get());
   }
   ```

2. Concurrency Tests
   ```java
   @Test
   public void testConcurrentIncrement() throws InterruptedException {
       AtomicLong counter = new AtomicLong(0);
       int threadCount = 10;
       int incrementsPerThread = 1000;

       ExecutorService executor = Executors.newFixedThreadPool(threadCount);
       for (int i = 0; i < threadCount; i++) {
           executor.submit(() -> {
               for (int j = 0; j < incrementsPerThread; j++) {
                   counter.incrementAndGet();
               }
           });
       }
       executor.shutdown();
       executor.awaitTermination(1, TimeUnit.MINUTES);

       assertEquals(threadCount * incrementsPerThread, counter.get());
   }
   ```

3. Stress Tests
   - Run with many threads
   - High iteration counts
   - Verify final state consistency

4. Performance Tests
   - Measure throughput
   - Compare with alternatives
   - Test under different contention levels

5. ABA Problem Tests
   - Test scenarios where ABA could occur
   - Verify correct behavior with stamped references

Testing Frameworks:

Best Practices:
---------------
1. Choose the Right Tool
   - AtomicLong: simple counters, low contention
   - LongAdder: high-contention counters
   - LongAccumulator: custom accumulation
   - Synchronized: complex operations

2. Minimize Contention
   - Use thread-local variables when possible
   - Batch updates
   - Consider striping pattern

3. Handle CAS Failures
   - Always check return value
   - Implement retry logic
   - Add backoff for high contention

4. Ensure Proper Visibility
   - Use AtomicLong for all shared access
   - Don't mix with regular long
   - Understand happens-before

5. Document Intent
   - Comment on thread-safety guarantees
   - Document invariants
   - Explain atomic operations

6. Test Thoroughly
   - Unit tests for correctness
   - Concurrency tests for thread-safety
   - Performance tests for optimization

7. Monitor in Production
   - Track CAS failure rates
   - Monitor contention
   - Profile under load

8. Avoid Common Pitfalls
   - Don't assume atomicity across operations
   - Don't ignore CAS failures
   - Don't use in tight loops without backoff
   - Don't forget about ABA problem

Anti-Patterns to Avoid:
-----------------------
1. Compound Operations Without Sync
   ```java
   // WRONG: Not atomic
   if (atomic.get() > threshold) {
       atomic.set(atomic.get() - amount);
   }
   ```

2. Ignoring Return Values
   ```java
   // WRONG: Doesn't handle failure
   atomic.compareAndSet(expected, newValue);
   ```

3. Mixing Atomic and Non-Atomic Access
   ```java
   // WRONG: Breaks visibility guarantees
   private long value;  // Not atomic
   private AtomicLong atomicValue;
   ```

4. Using for Complex State
   ```java
   // WRONG: Multiple variables need sync
   private AtomicLong x;
   private AtomicLong y;
   // Need to update x and y together atomically
   ```

5. Excessive Retries Without Backoff
   ```java
   // WRONG: Can cause CPU thrashing
   while (!atomic.compareAndSet(expected, newValue)) {
       expected = atomic.get();  // No backoff
   }
   ```

AtomicLong is a powerful tool for thread-safe operations on long values:

- Provides visibility guarantees
- Consider LongAdder for high-contention scenarios
- Understand limitations and use cases
- Test thoroughly for correctness
- Monitor performance in production

Key Takeaways:
- Use for simple shared counters and state
- Understand CAS and its limitations
- Handle contention appropriately
- Choose right tool for the job
- Test concurrent code thoroughly
- Monitor and tune based on workload
